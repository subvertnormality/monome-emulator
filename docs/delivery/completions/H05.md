## Apple Silicon execution resumed

An actual Apple Silicon host is now available: macOS15.3.2 on arm64 with Docker
Desktop4.69.0/Engine29.4.0. Its Linux VM is arm64 and buildx advertises amd64
emulation. The committed187db42 snapshot produced a pinned linux/amd64 image;
this lane is emulated amd64 and cannot establish a native arm64 result.

The first two startup-cancellation attempts are retained failures. Both timed out
in `docker run -d` before Docker created a container. A bounded mount probe then
showed that the image executes and `/private/tmp` bind mounts work, while a bind
mount below this host's protected Documents workspace blocks before container
creation. This is a host-runner portability boundary, not a native runtime crash.

Before changing the runners, H05 admits only the following narrow adaptation:
keep reports and copied diagnostic evidence under `artifacts/docker`, but stage
the runners' disposable host-mounted code/data under a canonical, Docker-shareable
temporary root on macOS. Record that root in each report. An explicit
`CONTAINER_MOUNT_ROOT` may override it. The code-edit, persistence, replacement,
isolation, unowned-data and conflicting-writer assertions remain unchanged and
must operate on those real host bind mounts. Do not copy a user project, silently
fall back after a mount failure, or reclassify either failed attempt as passed.

The focused launcher contracts also found that this macOS/Python combination can
bind a wildcard listener over an existing loopback listener on the same port when
the inherited HTTP server address-reuse option is enabled. Startup then contacted
the older server and returned a misleading token error instead of the required
port-collision failure. H05 therefore requires a bounded fixed-port occupancy
check before session creation: a live listener must fail explicitly, while a
stopped session must release the port for immediate intentional reuse. This
changes neither authentication nor the container's loopback-only host publishing
rule.

The first run against the rebuilt candidate reached Docker through the temporary
mount root, but exposed missing creation of the separate repository report
directory in the startup-cancellation runner. It produced no report and remains
a failed runner attempt. The bookkeeping correction creates only that report
directory; it does not change the container, runtime or acceptance assertions.

## Native arm64 continuation

The user approved the remaining native route after the Rosetta-configured retry.
This is a new, separately evidenced profile: `linux/arm64`, never an amendment of
the failed amd64 result. The official Ubuntu20.04 arm64 manifest is pinned to
`sha256:722ea796ac2d57eeb3627c58a582fc1acc58be51faf815e1bce1682ae5c092f7`.
A disposable native prerequisite build installed the same declared runtime/build
dependencies and resolved492 packages; the four-package difference from amd64
is architecture-specific rather than a relaxed dependency set.

Before implementation, H05 admits only an explicit `--platform linux/arm64`
export route selecting a distinct Dockerfile/package lock. Unknown platforms,
base mismatches, wrong image architecture and inventory drift must fail. The
amd64 profile and its failed evidence remain immutable. A committed native image
must then pass startup cancellation, browser, failures, restart, lease and
120-second audio in that order with host Chrome before the native row can pass.

The first native lease run is retained failed. Both containers became ready on
the same bind-mounted data root: Docker Desktop VirtioFS did not coordinate the
existing advisory `flock` across the two separately established bind mounts, and
the runner timed out waiting for the required rejection. Before a fix, H05 admits
an additional atomic directory sentinel under the owned data root. It complements,
not replaces, `flock`; stores a random owner token; is removed only by the matching
owner on graceful close; and remains conservatively blocking after an unclean
termination. The product must never steal a stale sentinel automatically because
that could admit two writers. Focused tests must simulate ineffective advisory
locking and prove second-writer rejection and owner-only cleanup before rebuilding
and restarting the six-gate sequence from gate1.
