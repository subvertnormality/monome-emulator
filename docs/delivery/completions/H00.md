## Inspected references

- [Winder norns-dev](https://github.com/winder/norns-dev/tree/a13ad4c2038184e093e9b1cbab234c7df23c059d),
  GPL-3.0. Its base is Debian 10.10 with separately built JACK/SC/libmonome;
  the test image pins official norns `740cbeed0fd4890f420d9fbc8691ccefbe73b5e4`
  and Maiden `1daf030c2c81b8d8fadadda22e1de5d1ec1381f1`, but uses a floating base
  image and floating script clones. tmuxp starts Xvfb, JACK, crone, matron and
  Maiden with sleeps. Dummy JACK is default; Linux audio instructions replace
  it with ALSA and pass `/dev/snd` plus the audio group. The README marks macOS
  unsupported. Adapt process topology only; keep our readiness checks, source
  pins, native framebuffer and virtual devices. No GPL source is copied.
- [Schollz norns-desktop](https://github.com/schollz/norns-desktop/tree/701f641b9285136c562892d9941452419ed131ef).
  No repository licence file was found; do not infer permission from its
  relationship to Winder. No source/assets/scripts will be copied. The Dockerfile
  uses Debian Bookworm, amd64 Go and community norns/Maiden forks; startup uses
  fixed ports, sleeps, Xvfb, an image-capture server and ws-wrapper. JACK feeds
  DarkIce then Icecast MP3 (`bufferSecs=1`), with Caddy routing the editor/REPL
  and stream. That suggests a portable monitoring route, not low-latency proof.
  Its README first excludes external grid/MIDI/audio input, then gives grid
  and ALSA instructions; those claims are inconsistent, not host acceptance.
  Restart scripts kill processes by broad name matching. We retain owned PIDs,
  per-session ports/data, current controls and existing PCM/worklet playback.
- [Official Maiden](https://github.com/monome/maiden/tree/2e64f7d59284962ac68055dd556e3fd8515462f8),
  GPL-3.0. Proposed separate pinned runtime component, retaining licence and
  corresponding-source/distribution records; no re-licensing as MIT. Its server
  supports `--app`, `--data`, `--doc` and `--fd`; the latter accepts a launcher
  supplied loopback listener. Its web client reads `repl-endpoints.json`, uses
  WebSocket subprotocol `bus.sp.nanomsg.org`, newline for Lua and ESC for SC.
  Go and web dependencies have their own manifests; build tools/assets need
  pinned identities in the optional Maiden component bundle.

## Runtime/fork comparison

Inspected the exact reference norns fork
`8e72d2015e1a966c023834a24e6a6fbe998e2ce4`: its tip changes a font to Particle;
that is unrelated to our missing audio/editor capabilities and is not adopted.
The reference Dockerfile additionally rewrites tape disk and screensaver code;
those are not needed for this integration and are not copied.

Inspected Maiden fork `ce4471e25a45c87040817c0619f3596fa43060aa` and preceding
`f008c755a5c41c957b7f7fc60e9a443b8a1866fc`: systemd operations are replaced with
hardcoded restart scripts. Current official Maiden instead explicitly returns
503 when D-Bus is absent. Its `.sc`/`.scd` text MIME override is already upstream
(`cmd/server.go`, issue 219 comment). No fork patch is required for either.

Our pinned official norns `14bbeae8646c6717f6bb44c8cd60250bf94b6042` already has
stdin-driven matron execution and configurable service ports. Existing launcher
children have stdin pipes and owned output logs. Prefer a small WebSocket/stdio
adapter to these official interfaces. The official ws-wrapper is informative,
but returns zero after a child fails; blindly replacing our process ownership
with it would lose the strict exit checks. Do not do that. If implementation
reveals a necessary runtime patch, document its official base, rationale and
removal condition before adding it, and check official upstream first.

Windows Docker client 20.10.17 is installed; its engine named pipe is absent.
The WSL Docker shim reports integration unavailable. No daemon or integration
setting was changed by this audit. Go is not in the WSL login PATH. These are
dependency findings, not platform failure claims. H04 can inspect/start the
installed Docker service when eligible or record an exact setup blocker; it
must not replace WSL or assert macOS support. No macOS host is currently present.

## Plan review refinements

The H00 Codex review identified three consequential gaps. These requirements
are mandatory refinements of the table, not optional follow-up work:

- **Maiden navigation (H02):** official Maiden's directory response uses
  `DirEntry.IsDir()`, which treats our linked application directories as files.
  Keep the existing external editable code mapping. Prepare a narrow patch in
  the separately licensed official Maiden component that follows directory
  symlinks when constructing directory children (`os.Stat` with explicit errors),
  after confirming the current official pin still requires it. Record the
  official base, GPL attribution, patch digest and removal condition: an upstream
  implementation that passes the same navigation test. Do not copy this GPL
  server implementation into MIT core. Browser acceptance must start at the
  real dust tree root, expand the launcher-created linked application directory,
  select, edit, save and run that same file, then assert changed native output.
  A direct file URL or test-only file write cannot substitute for navigation.
- **Recoverable REPL workflow (H02):** keep sticky native engine failure detection.
  The first implementation recovers a faulted interpreter through an explicit
  owned session restart in the editor integration, not by clearing `errors` or
  suppressing arbitrary SC `ERROR:` lines. The editor must show the diagnostic
  and the restart action. Restart replaces only that session's services and
  relay generation, reopens its owned dataset, and reconnects the editor; it
  never restarts host services. Test an erroneous SC command, visible diagnostic,
  this declared recovery, a successful corrected command, and working native
  browser controls plus actual audio afterward. Also retain an injected real
  engine failure assertion: it must remain an explicit failure. If a later
  implementation separates interactive diagnostics from engine failures, that
  classification needs evidence and focused review before replacing this gate.
- **Persistent datasets (H02 prerequisite, reused by H04):** fresh launches retain
  today's fresh-data default. Add an explicit reopen option for a dataset created
  and marked as owned by this launcher. Its metadata identifies the dataset,
  application mapping and schema independently of the transient process/session
  ID. Refuse arbitrary unmarked directories and concurrent writable attachment;
  use a held OS file lock released on process exit. Preserve application files
  verbatim. Recreate only a documented allowlist of launcher-generated system
  startup files (state, enabled-mod list and keyboard layout) to update temporary
  paths; never silently adopt or overwrite an existing user project. Application
  code may be edited in place, but mismatched application mappings are explicit
  errors. Test fresh sessions remain distinct, explicit reopening restores a
  runtime-saved value without reseeding, contention rejects a second writer,
  and cleanup releases ownership. For H04 additionally destroy and recreate the
  container/session, attach that dataset and recover the saved behavior through
  runtime/browser inputs without test-only reseeding. Retained files without
  recovered behavior do not pass persistence acceptance.
